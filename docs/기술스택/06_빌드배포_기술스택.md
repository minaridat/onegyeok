# 빌드/배포 기술 스택 — electron-builder + 네이티브 헬퍼 패키징

> 메인 기술 스택: [00_메인_기술스택.md](./00_메인_기술스택.md) 5장(패키징/배포)의 상세 버전
> 상태: 🚧 설계 — electron-builder 설정은 아직 실제로 빌드/검증 전(아래 체크리스트 참고)

## 왜 이 문서가 필요한가

RDP/VNC가 Apache Guacamole(외부 Docker 의존성)에서 **`libfreerdp`/`libvncclient`를 직접 링크한
네이티브 헬퍼**(`native/rdp-helper/`, `native/vnc-helper/`)로 바뀌면서, "서버 설치 없이 앱만 설치해서
쓴다"는 원래 목표에 가까워진 대신 **패키징이 더 복잡해졌다** — 순수 JS Electron 앱이 아니라, OS/아키텍처별로
컴파일된 네이티브 바이너리 2개를 같이 담아 배포해야 한다. 이 문서는 "실제 설치파일(.dmg/.exe)을 어떻게
만들 것인가"를 다룬다. 각 프로토콜 자체의 설계는 [03_RDP_기술스택.md](./03_RDP_기술스택.md)/
[04_VNC_기술스택.md](./04_VNC_기술스택.md)를 참고.

## 현재 상태 요약

| 항목 | macOS | Windows |
|---|---|---|
| 네이티브 헬퍼 컴파일 | ✅ 검증됨(Homebrew `freerdp`/`libvncserver` + `make`) | 🔲 미검증 — 아래 "Windows 빌드" 참고 |
| 실제 RDP/VNC 서버 접속 | ✅ xrdp/VNC 테스트 컨테이너로 end-to-end 검증 | 🔲 미검증(NLA 포함) |
| electron-builder 설정 | 🔲 미작성(이 문서의 제안안만 있음) | 🔲 미작성 |
| 패키징된 앱의 헬퍼 경로 해석 | ✅ `app.isPackaged` 분기 코드 반영됨(`helper-bridge.js`) | ✅ 동일 코드(플랫폼 분기 포함), 실제 패키징으로는 미검증 |
| 코드사이닝/공증 | 🔲 정책 미결정 | 🔲 정책 미결정 |

## 1. 개발 중 빌드(지금 당장 되는 것)

```bash
npm install
npm run build:native   # native/rdp-helper, native/vnc-helper를 현재 OS/아키텍처용으로 컴파일
npm start
```

`npm run build:native`는 `make -C native/rdp-helper && make -C native/vnc-helper`다. 두 헬퍼의
`Makefile`은 지금 **macOS(clang + Homebrew pkg-config) 전용**이다 — Windows에서는 그대로 안 돌아간다
(아래 2장).

**워크트리/클론마다 한 번씩 실행해야 한다** — 컴파일된 바이너리(`onegyeok-rdp-helper`,
`onegyeok-vnc-helper`)는 `.gitignore` 대상이라 git에 들어있지 않다(실사용 중 이 때문에 `spawn ENOENT`가
난 적이 있다 — `helper-bridge.js`의 에러 메시지에 이제 힌트가 붙는다).

## 2. Windows에서 네이티브 헬퍼 빌드 (미검증 — 해야 할 일)

현재 `Makefile`은 `clang`과 `pkg-config`에 의존하는데, 이게 Windows 기본 환경에는 없다. 필요한 작업:

1. **빌드 의존성 확보**: `vcpkg install freerdp3 libvncserver`(또는 FreeRDP/LibVNCServer 공식 Windows
   빌드 가이드대로 직접 빌드) — FreeRDP는 Windows 공식 빌드 문서가 있고(`guacd`보다 훨씬 성숙), `libvncclient`도
   Windows 빌드가 가능하다고 알려져 있지만, 이 리포에서 실제로 해본 적은 없다.
2. **빌드 스크립트 포팅**: `clang`+`pkg-config` 기반 `Makefile`을 MSVC(`cl.exe`/`nmake`) 또는 `CMakeLists.txt`로
   바꿔야 한다. 두 헬퍼 모두 소스가 작고(`src/main.c` + `framing.c` + `jsonlite.c`) 외부 의존성이 FreeRDP/
   LibVNCServer 하나뿐이라, CMake로 바꾸는 작업 자체는 크지 않을 것으로 예상되지만 **실제로 컴파일해보기
   전까지는 추정일 뿐**이다 — vcpkg 패키지 이름, `.lib`/`.dll` 링크 방식, 헤더 경로가 macOS Homebrew와
   다를 수 있다.
3. **런타임 DLL 배포**: 정적 링크가 안 되면 `freerdp3.dll`/`winpr3.dll`/`libvncclient.dll` 등을 헬퍼
   바이너리와 같은 디렉터리에 같이 배포해야 한다(macOS는 Homebrew의 공유 라이브러리를 그대로 썼지만,
   배포용 macOS 빌드에서도 결국 같은 문제가 있다 — 3장 참고).
4. **Windows Server 대상 NLA 검증**: 지금까지는 구버전 xrdp 컨테이너로 TLS 보안만 확인했다. 실제 Windows
   RDP는 기본이 NLA라, 이것도 실제 Windows 환경에서 검증해야 한다.

이 작업은 **실제 Windows 머신(또는 VM)이 있어야 가능**하다 — 지금 이 macOS 환경에서는 여기까지만 할 수 있다.

## 3. macOS 배포 시 라이브러리 의존성 문제 (아직 해결 안 됨)

지금까지의 빌드/테스트는 전부 **이 머신에 이미 설치된 Homebrew의 `freerdp`/`libvncserver`**를 동적
링크해서 됐다. 사용자 PC에는 당연히 이 라이브러리들이 없다 — 배포용 바이너리는 둘 중 하나를 해야 한다:

- **정적 링크**로 바꿔서 외부 `.dylib` 의존성을 없앤다(`FreeRDP`/`LibVNCServer`를 `-static` 빌드하거나
  직접 소스에서 정적 라이브러리로 빌드), 또는
- **`dylib`를 헬퍼 바이너리와 같이 번들링**하고 `install_name_tool`/`@rpath`로 상대 경로를 잡아준다
  (macOS 앱 배포에서 흔한 패턴 — `electron-builder`의 `extraResources`에 `.dylib`들도 같이 넣고, 빌드
  후처리 스크립트로 `@rpath`를 재작성해야 한다).

**아직 둘 중 뭘 할지 결정도, 시도도 안 했다** — 지금 개발 중 빌드가 되는 건 전적으로 이 머신에 Homebrew가
깔려 있기 때문이고, 그걸 다른 Mac에 그대로 복사하면 `dyld: Library not loaded` 류 에러가 날 것이다.

## 4. `electron-builder` 설정 (제안안 — 미검증)

`devDependencies`에 추가:

```bash
npm install --save-dev electron-builder
```

`package.json`에 추가할 `build` 블록 제안(실제로 빌드 안 해봤으므로 필드명/경로는 검증 필요):

```jsonc
"build": {
  "appId": "com.onegyeok.app",
  "productName": "onegyeok",
  "directories": { "output": "dist" },
  "files": [
    "src/**/*",
    "package.json",
    "node_modules/**/*"
  ],
  "extraResources": [
    // 네이티브 헬퍼 실행 파일(+ macOS면 동적 링크된 .dylib까지, 3장이 해결되면)을
    // resourcesPath/native/<proto>-helper/ 밑에 그대로 복사 — helper-bridge.js의
    // resolveHelperPath()가 app.isPackaged일 때 이 경로를 그대로 찾는다.
    { "from": "native/rdp-helper", "to": "native/rdp-helper", "filter": ["onegyeok-rdp-helper*", "!*.c", "!*.h", "!Makefile", "!test"] },
    { "from": "native/vnc-helper", "to": "native/vnc-helper", "filter": ["onegyeok-vnc-helper*", "!*.c", "!*.h", "!Makefile", "!test"] }
  ],
  "mac": {
    "target": ["dmg"],
    "category": "public.app-category.developer-tools",
    "hardenedRuntime": true
  },
  "win": {
    "target": ["nsis"]
  }
}
```

중요한 점: 네이티브 헬퍼는 **asar 압축 대상이 아니라 `extraResources`**로 넣어야 한다 — asar 아카이브
안에 있는 실행 파일은 OS가 직접 `spawn()`으로 실행할 수 없다(Electron이 자동으로 asar 안의 특정 파일
요청을 가로채 꺼내주는 건 `fs` 모듈 호출에 한정되지, `child_process.spawn`의 실행 파일 경로에는 적용 안
된다).

## 5. 패키징된 앱에서의 헬퍼 경로 해석 (코드 반영 완료)

`src/main/protocols/{rdp,vnc}/helper-bridge.js`의 `resolveHelperPath()`가 이제 이렇게 분기한다:

1. `ONEGYEOK_RDP_HELPER_PATH`/`ONEGYEOK_VNC_HELPER_PATH` 환경변수가 있으면 최우선(개발/테스트용 오버라이드).
2. `app.isPackaged`면 `process.resourcesPath/native/<proto>-helper/<bin>` — 위 4장의 `extraResources`
   설정과 짝을 이룬다.
3. 그 외(개발 중, `npm start`로 소스에서 직접 실행)에는 리포 루트의 `native/<proto>-helper/<bin>`.

**이 코드는 작성됐지만, electron-builder로 실제 패키징해서 `.app`/`.exe`를 열어본 적은 없다** — 2번
분기가 실제로 맞는지는 다음 체크리스트의 "실제 패키징 시도" 항목에서 처음 검증된다.

## 6. 코드사이닝 / 공증 — 아직 결정 안 됨

[00_메인_기술스택.md](./00_메인_기술스택.md) 5장에 이미 적혀 있던 내용 그대로, 아직 결론이 안 났다:

- **macOS**: Apple Developer ID로 서명 + 공증(notarization) 없이 배포하면 Gatekeeper가 "확인되지 않은
  개발자" 경고를 띄운다 — 사내 배포(사이드로드)만 할 거면 감수 가능하지만, 사용자가 매번 "확인 없이 열기"를
  눌러야 한다.
- **Windows**: Authenticode 서명 없이 배포하면 SmartScreen이 비슷한 경고를 띄운다.
- 둘 다 **사내 배포 정책(서명 인증서를 발급받을지, 사이드로드를 허용할지)을 먼저 정해야** `electron-builder`의
  `mac.identity`/`win.certificateFile` 설정을 채울 수 있다 — IT/보안 담당자 확인 필요.

## 7. CI 파이프라인 제안 (아직 안 만듦)

GitHub Actions에 플랫폼별 매트릭스로 "네이티브 헬퍼 빌드 + electron-builder 패키징"을 자동화하는 게
자연스럽다 — 특히 Windows는 이 리포에서 아무도 로컬로 매번 검증하기 어려우니, CI가 사실상 유일한
지속적 검증 수단이 된다.

```yaml
# 제안안 — 아직 작성/실행 안 함
strategy:
  matrix:
    include:
      - os: macos-14      # Apple Silicon
      - os: macos-13      # Intel
      - os: windows-latest
steps:
  - uses: actions/checkout@v4
  - uses: actions/setup-node@v4
  - run: npm install
  # macOS: brew install freerdp libvncserver pkg-config && npm run build:native
  # Windows: vcpkg install freerdp3 libvncserver (2장 포팅 완료 후)
  - run: npx electron-builder
  - uses: actions/upload-artifact@v4
```

## 8. 체크리스트 (배포 전 반드시 확인)

- [ ] `native/*/Makefile`을 Windows에서 빌드 가능하게 포팅(CMake 전환 유력) — 2장
- [ ] 실제 Windows 머신/VM에서 두 헬퍼 컴파일 + 실제 Windows Server RDP(NLA) 접속 검증
- [ ] macOS 배포용 바이너리의 `freerdp`/`libvncclient` 의존성 해결(정적 링크 또는 `.dylib` 번들링) — 3장
- [ ] `electron-builder` 설치 + 4장 설정으로 실제 `.dmg`/`.exe` 빌드 시도
- [ ] 패키징된 앱을 **Homebrew가 깔려 있지 않은 깨끗한 macOS**에서 실행해 헬퍼가 정상 spawn되는지 확인(지금까지의 모든 검증은 Homebrew 의존성이 있는 개발 머신에서만 이뤄졌다)
- [ ] 코드사이닝/공증 정책 확정(6장) 후 CI에 인증서 시크릿 연결
- [ ] GitHub Actions 빌드 매트릭스 작성(7장)
