## 2. 현재 프로젝트 구조

```
onegyeok/
├── package.json
├── package-lock.json
├── .gitignore
├── docs/                   # 기획/기능명세/기술스택 문서 (이 폴더)
├── src/
│   ├── main/
│   │   ├── main.js          # BrowserWindow 생성, IPC 핸들러, 종료 시 세션 강제종료 훅(F-502)
│   │   ├── ssh-manager.js   # SSH 연결 관리 (01_SSH_기술스택.md)
│   │   └── db-manager.js    # SQL DB 연결 관리 (02_SQL_기술스택.md)
│   ├── preload/
│   │   └── preload.js       # contextBridge로 window.onegyeok API 화이트리스트 노출
│   └── renderer/
│       ├── index.html       # 앱 UI (서버 트리·탭·서버관리·인스펙터)
│       ├── styles.css
│       ├── renderer.js      # UI 상태/인터랙션 로직
│       └── vendor/           # xterm.js 정적 번들
```

- `src/main`, `src/preload`, `src/renderer` 3분할은 Electron 보안 권장 구조(프로세스 격리)를 그대로 따른다.
- RDP/VNC/SFTP가 구현되면 `src/main`에 `ssh-manager.js`/`db-manager.js`와 같은 패턴으로 `rdp-manager.js` 등을 추가하고,
  `main.js`의 `terminateAllSessions()`에 각 매니저의 `disconnectAll()`을 등록한다(F-502).

## 3. Electron 프로세스/보안 구조

- `BrowserWindow`는 `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`로 생성한다(현재 `src/main/main.js`에 적용됨). 렌더러는 Node API에 직접 접근할 수 없고, `preload.js`가 `contextBridge.exposeInMainWorld`로 노출한 최소 API(`window.onegyeok.*`)만 사용한다.
- IPC 채널을 추가할 때도 **화이트리스트 원칙**을 유지한다 — `ipcRenderer.invoke`를 preload에서 임의 채널명으로 노출하지 않고, 채널별로 명시적 함수를 하나씩 추가한다(현재 `ssh.*`, `db.*` 네임스페이스 패턴을 따름).
- 앱 종료(F-502) 처리는 `app.on('before-quit')`에 훅이 있다(`terminateAllSessions()`) — 현재 `sshManager.disconnectAll()`과 `dbManager.disconnectAll()`을 호출한다. 새 프로토콜 매니저가 추가되면 여기에 추가한다.

## 4. 보안 스택 상세 (ISMS-P 대응, [공통 기능명세](../기능명세/00_공통_기능명세.md) F-601~609)

- **로컬 데이터 암호화**: Node 내장 `crypto` 모듈의 AES-256-GCM. 별도 암호화 라이브러리를 추가하지 않아도 Node 표준 API로 충분하다.
- **키 유도(KDF)**: 마스터 패스워드 → 암호화 키 파생에는 **PBKDF2**(`crypto.pbkdf2`, Node 내장, 네이티브 빌드 불필요)를 1차로 채택한다. Argon2id가 이론적으로 더 안전하지만 `argon2` 패키지는 네이티브 addon이라 플랫폼별 빌드 부담이 생긴다 — 초기 설치 단순성을 우선해 PBKDF2(반복 횟수 충분히 높게 설정, 예: 600,000회 이상 — OWASP Password Storage Cheat Sheet의 PBKDF2-HMAC-SHA256 최신 권장치)로 시작하고, 추후 필요 시 Argon2id로 전환 가능하도록 KDF 로직을 모듈화해둔다(F-608의 "암호 모듈 교체 가능" 요구사항과도 일치).
- **OS 자격증명 저장소 연동**: `keytar`는 Electron 생태계에서 널리 쓰였지만 **현재 유지보수가 중단(archived)** 되어 있어 신규 채택에는 비권장. 대신 Electron 자체에 내장된 **`safeStorage` API**(OS Keychain/Windows DPAPI/libsecret을 내부적으로 래핑, 외부 의존성 없음)를 사용한다. **서버별 메모 저장에 실제 적용 완료** — `src/main/main.js`의 `memo:save`/`memo:load-all`/`memo:rename` IPC 핸들러가 `safeStorage.encryptString`/`decryptString`으로 `userData/memos.json`에 암호화 저장한다. `safeStorage.isEncryptionAvailable()`이 `false`인 환경(예: 키링 없는 일부 Linux)에서는 저장을 건너뛰고 UI에 "저장 불가" 상태를 표시하도록 처리했다.
- **접속 로그 저장**: 초기에는 append-only **JSON Lines 파일**로 단순하게 시작한다(수정·삭제 API를 아예 만들지 않는 것으로 "위변조 방지" 요구를 1차 충족). 로그량이 늘거나 검색/필터가 필요해지면 `better-sqlite3`로 전환을 검토한다.

## 5. 패키징/배포

- **`electron-builder`** 를 권장한다 — macOS/Windows 설치파일 빌드, 코드사이닝, 자동 업데이트까지 생태계가 가장 성숙하다 (`electron-forge`도 대안이나 플러그인 구조가 상대적으로 무겁다).
- 사내 배포 전용 도구이므로 정식 공증(macOS notarization)·코드사이닝 인증서가 필수인지는 **사내 배포 정책에 따라 결정** — 사이드로드(서명 없이 내부 배포) 허용 여부를 IT/보안 담당자와 확인 필요.
- RDP/VNC가 네이티브 헬퍼(`libfreerdp`/`libvncclient` 직접 링크)로 바뀌면서 패키징이 단순한 Electron
  빌드보다 복잡해졌다(OS/아키텍처별 바이너리 동봉, Windows 빌드 포팅 등 미해결 항목 다수) — 상세 내용과
  체크리스트는 [06_빌드배포_기술스택.md](./06_빌드배포_기술스택.md) 참고.

## 6. 개발 도구 및 향후 전환 로드맵

- **린트/포맷**: ESLint + Prettier 도입 예정(아직 미설정) — 특히 IPC 채널명 오타, `contextBridge` 노출 범위 실수를 잡는 데 유용.
- **TypeScript 전환 검토**: 현재는 빠른 스캐폴딩을 위해 순수 JS로 시작했다. 연결 관리자처럼 상태가 복잡해지는 시점(RDP/VNC 추가 등)에 TypeScript로 전환하면, 특히 `preload`↔`renderer` 간 IPC 계약(타입)을 공유해 오류를 줄일 수 있다. 지금 당장 급하지 않으므로 "검토" 상태로 둔다.
- **테스트**: 아직 테스트 프레임워크 미도입. 연결 관리자(상태 머신)부터 단위 테스트를 붙이는 것을 권장 — Vitest 또는 Node 내장 `node:test` 러너 둘 다 적합, 별도 결정 필요. (현재 e2e 검증은 Playwright로 실제 Electron 앱을 구동해 수동 스크립트로 수행 중 — 저장소에는 포함되지 않음)

## 7. 필요 기술 역량 (팀 스킬셋)

실제 구현을 맡을 인력이 갖추면 좋은 역량을 정리한다 — 채용/역할분담 참고용.

| 역량 | 왜 필요한가 |
|---|---|
| Electron/Node.js 데스크톱 앱 개발 경험 | 메인/프리로드/렌더러 프로세스 구조, IPC 보안 모델 이해 필수 |
| 네트워크 프로토콜 기초 (SSH/RDP/VNC/SFTP/SQL) | 각 프로토콜의 인증·세션·암호화 방식을 알아야 올바른 라이브러리 선택·디버깅 가능 |
| 네이티브 모듈 빌드 대응력 (`node-gyp` 등) | RDP([03_RDP_기술스택.md](./03_RDP_기술스택.md) 옵션 C) 등에서 플랫폼별 네이티브 addon 빌드가 필요할 수 있음 |
| 보안/암호화 기초 지식 (AES-GCM, KDF, OS Keychain) | ISMS 요구사항(4장)을 코드 리뷰 수준에서 검증하려면 필요 |
| 프런트엔드 바닐라 JS/CSS | 현재 렌더러는 프레임워크 없이 직접 DOM 조작(`src/renderer/renderer.js`) — React 등 프레임워크 경험보다 바닐라 DOM/CSS Grid 이해가 더 직접적으로 쓰임 |
| macOS/Windows 패키징·배포 경험 (선택) | 5장 배포 단계에서 필요, Phase1 구현 자체에는 필수 아님 |

## 8. 버전 관리 정책

- `package-lock.json`은 항상 커밋한다(이미 적용 중) — Electron 같은 대형 바이너리 의존성의 버전 드리프트를 막기 위함.
- Electron 메이저 버전 업그레이드는 기능 변경과 섞지 않고 **별도 커밋/PR로 분리**, 릴리즈 노트의 보안 수정 사항을 확인한 뒤 진행한다.
