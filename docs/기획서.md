# onegyeok 기획서

> "SSH, RDP, VNC, FTP... 한 개(one)로 다 끝(gyeok)"
> 서버/인프라 엔지니어를 위한 올인원 원격 접속 클라이언트

---

## 1. 개요

| 항목 | 내용 |
|---|---|
| 프로젝트명 | onegyeok |
| 한 줄 정의 | Windows/Mac에서 동작하는 SSH(+tmux) · RDP · VNC · SFTP/FTP 통합 원격 접속 클라이언트 |
| 타겟 사용자 | 서버/인프라 엔지니어, DevOps, SRE, 여러 프로토콜을 매일 오가며 서버를 관리하는 실무자 — **특히 ISMS(-P) 인증 심사를 받는 기업의 인프라팀** |
| 배경 | Termius(SSH+tmux), Royal TSX/RDP 클라이언트, VNC Viewer, FileZilla Pro 등 각 기능이 프로그램별로 분산되어 있고 대부분 유료. 사내에서 실사용 가능한 통합 도구가 필요 |
| 핵심 가치 | "따로 사던 걸 하나로" — 여러 유료 클라이언트를 대체하는 올인원 도구 |
| 보안 전제 | 사내 ISMS 인증 심사 대상 자산으로 사용될 것을 전제로 설계. **심사위원 확인 요구사항에 따라 자동로그인(비밀번호 저장) 기능은 전면 폐기** — 모든 인증은 접속 시 사용자가 직접 입력하며, 그 외 접속 로그·세션 강제 종료 등 보호대책을 반영 |

## 2. 문제 정의

인프라 엔지니어는 하루에도 여러 프로토콜을 오간다.

- SSH 터미널 + tmux 세션 유지 (Termius 유료 기능)
- 윈도우 서버 원격 데스크톱 (RDP 클라이언트)
- 리눅스 GUI 서버 (VNC)
- 파일 업/다운로드 (FileZilla Pro급 SFTP/FTP)
- 사내 admin 웹 콘솔 (사내 시스템, 클라우드 콘솔 등)

→ 현재는 이 5가지를 각각 다른 프로그램으로 쓰고 있고, 각 프로그램은 개별적으로 유료 결제가 필요함.
→ **하나의 프로그램에서 서버를 "등록"만 하면 프로토콜에 맞게 바로 접속**되는 도구가 없음.

## 3. 핵심 기능

### 3.1 통합 서버 등록 (Connection Manager)
- 서버 등록 시 프로토콜 선택(SSH / RDP / VNC / SFTP·FTP / Web)
- 프로토콜별 접속 정보(호스트, 포트, 인증방식 등) 입력
- 등록 후 클릭 한 번으로 해당 프로토콜 클라이언트가 즉시 실행되는 "빠른 연결"
- 서버 그룹/폴더/태그 분류 (환경별: 운영/스테이징/개발, 팀별 등)

### 3.2 SSH 클라이언트 (Termius 대체)
- SSH 접속 + 내장 터미널
- tmux 유사 세션 관리: 세션 유지, 다중 탭/분할, 접속 끊겨도 세션 복구
- 키 기반 인증 / 패스워드 인증 지원
- 포트 포워딩(로컬/원격), Jump host(Bastion) 지원
- **다중 서버 동시 명령 실행 (Broadcast / Multi-Exec)**: 여러 SSH 탭을 선택해 하나의 입력을 동시에 전송 — tmux `synchronize-panes`, Termius의 유료 "Multi Exec" 기능과 동일한 개념. 동시 입력 중에는 경고 배너로 오탐(잘못된 서버에 명령 전송)을 방지

### 3.3 RDP 클라이언트
- Windows 서버 원격 데스크톱 접속
- 해상도/클립보드 공유/드라이브 마운트 등 기본 RDP 옵션

### 3.4 VNC 클라이언트
- VNC 서버 접속, 압축/화질 옵션 조정

### 3.5 SFTP/FTP 클라이언트 (FileZilla Pro 대체)
- SSH 등록 정보 재사용한 SFTP 파일 탐색기
- 드래그앤드롭 업/다운로드, 동기화, 다중 전송 큐

### 3.6 수동 인증 입력 (자동로그인 기능 폐기)
> ⚠️ **정책 변경**: 최초 기획 단계에서는 "비밀번호 자동 저장 → 자동 로그인"을 핵심 차별화 기능으로 설계했으나,
> 사내 보안 담당자 확인 결과 **ISMS 인증 심사에서는 심사위원 앞에서 비밀번호를 직접 입력하는 절차가 요구**되어
> 자동로그인/비밀번호 저장 기능은 전면 폐기한다. 앱 어디에도 로그인용 비밀번호를 저장하지 않는다.

- 비밀번호 인증 서버는 **접속할 때마다 사용자가 직접 비밀번호를 입력**한다 (저장/자동입력 없음)
- SSH Key 인증 시 키 **파일 경로**는 등록 정보로 저장할 수 있으나(파일 자체가 비밀이 아님), **Passphrase는 저장하지 않고 접속마다 직접 입력**한다
- 단, 키 기반 인증은 비밀번호 자체가 없으므로 심사 요구사항(패스워드 직접 입력)과 무관하게 그대로 사용 가능 — 오히려 비밀번호 인증보다 권장되는 방식
- 서버 측 정책으로 비밀번호가 만료된 경우에도 별도의 감지·안내 기능 없이 **일반 인증 실패와 동일하게 처리**한다 — 사용자가 서버에서 직접 비밀번호를 변경한 뒤 다시 접속하면 된다 (저장/자동전환 기능 자체가 없으므로 별도 UX를 둘 실익이 작다고 판단해 폐기)

### 3.7 웹페이지(Admin 콘솔) 등록
- 사내 admin 페이지, 클라우드 콘솔(AWS/GCP 등) URL을 서버 목록에 함께 등록
- 클릭 시 기본 브라우저(또는 내장 웹뷰)로 바로 이동
- ~~계정 정보(ID 자동입력) 연동~~ — 자동로그인 폐기 정책(3.6)에 따라 미지원. 북마크(URL 바로가기) 용도로만 사용

### 3.8 서버 관리 (전체 목록/편집)
- 트리·탭 화면과 별개로, **등록된 모든 서버를 한 화면의 테이블(그리드)로 조회**
- 이름/그룹/프로토콜/호스트/포트/인증 방식/마지막 접속일 등을 컬럼으로 표시, 검색·정렬·프로토콜별 필터링
- 테이블에서 바로 편집(더블클릭 또는 편집 버튼) — IP, 포트, 이름, 그룹, 인증 방식 등 모든 등록 필드 수정 가능 (비밀번호 필드는 없음 — 저장하지 않으므로)
- 다중 선택 후 일괄 삭제/그룹 이동 지원

### 3.9 보안 요구사항 (ISMS-P 대응)
사내 ISMS 인증 심사 대상 도구로 쓰이는 것을 전제로, 다음을 설계 단계부터 반영한다.

- **자동로그인 기능 전면 폐기**: 비밀번호는 어떤 형태로도 저장하지 않으며, 접속 시마다 사용자가 직접 입력한다 (심사위원 확인 요구사항 대응). SSH Key passphrase도 동일하게 매번 직접 입력
- **로컬 서버 목록 암호화**: 비밀번호는 저장하지 않지만, 호스트/IP/그룹 등 인프라 토폴로지 정보 자체도 민감 자산이므로 로컬 저장 데이터는 AES-256-GCM 등으로 암호화 보관
- **앱 자체 접근 통제**: 마스터 패스워드(또는 OS 생체인증)로 앱 실행 자체를 보호 — 서버 목록 열람 통제 목적. 일정 시간 유휴 시 자동 잠금
- **접속 이력 로깅**: 모든 서버 접속 시도(성공/실패, 일시, 대상 서버, 프로토콜)를 로컬에 기록 — 심사 시 접속 이력 제출 대응
- **로그 위변조 방지**: 접속 로그는 앱에서 수정·삭제 불가능한 형태로 보관
- **연결 유지 vs 강제 종료의 구분**:
  - 프로토콜 전환(왼쪽 레일)이나 탭 이동 중에는 기존 연결을 끊지 않는다 (업무 연속성)
  - 반면 **프로그램 자체를 종료할 때는 예외 없이 모든 활성 연결(SSH/RDP/VNC/SFTP/Web)을 강제 종료**한다 (보안 요구사항). 서버 측 tmux 프로세스 자체는 남아 있어도 무방 — PC 클라이언트↔서버 간 통신 세션만 대상
- **전송구간 보호**: VNC처럼 자체 암호화가 약한 프로토콜은 SSH 터널링 등 보호 수단을 기본값으로 권장

> 세부 알고리즘·로그 스펙은 [기능명세/00_공통_기능명세.md](./기능명세/00_공통_기능명세.md)의 "보안 아키텍처" 절 참고.

## 4. 사용 흐름 (User Flow)

```
[서버 등록]
  ↓ 프로토콜 선택 (SSH/RDP/VNC/SFTP/Web)
  ↓ 접속 정보 입력 (비밀번호는 저장하지 않음, SSH Key는 파일 경로만 저장)
[서버 목록]
  ↓ 클릭 = 프로토콜에 맞는 클라이언트 실행 + 비밀번호(또는 Key Passphrase) 직접 입력
[접속 중]
  - SSH: tmux 세션 유지
  - RDP/VNC: 원격 화면 제어
  - SFTP: 파일 전송
  - Web: 콘솔 페이지 오픈
```

## 5. 경쟁 제품 대비 차별점

| 제품 | 커버 영역 | 비용 | onegyeok 차별점 |
|---|---|---|---|
| Termius | SSH, 일부 SFTP | tmux/sync 등 유료 | RDP/VNC/Web까지 통합 |
| Royal TSX / mRemoteNG | RDP 중심 멀티프로토콜 | Royal TSX 유료 | UX 단순화 + 다중 서버 동시 실행 |
| VNC Viewer | VNC only | 상업용 유료 | 통합 등록/관리 |
| FileZilla Pro | FTP/SFTP | 유료 | SSH 세션과 연동된 파일 관리 |

→ onegyeok의 핵심은 **"기능 총합" + "서버 등록 한 번으로 프로토콜 자동 매핑" + "다중 서버 동시 명령 실행" + "ISMS 심사 대응 가능한 보안 기본값(자동로그인 없음)"**

## 6. 기술 스택 (확정)

- **크로스플랫폼 데스크톱**: **Electron 채택 확정** (Windows/Mac 동시 지원) — RDP/VNC 네이티브 바인딩과 라이브러리 생태계가 풍부해 Phase 2~5 확장에 유리하다고 판단
- **터미널/SSH**: xterm.js + ssh2 (Node.js) 혹은 libssh2 바인딩
- **RDP**: FreeRDP 연동(네이티브 바인딩) 또는 기존 OS RDP 클라이언트 프로세스 제어
- **VNC**: noVNC(웹뷰 기반) 또는 native VNC 라이브러리
- **SFTP/FTP**: ssh2-sftp-client, basic-ftp
- **로컬 데이터 보호**: 비밀번호는 저장하지 않음 — 서버 목록(호스트/IP/그룹 등) 로컬 저장소는 앱 자체 암호화 레이어로 보호, 앱 잠금은 OS Keychain/Credential Manager(마스터 패스워드 기반 키) 연동

## 7. 개발 우선순위 (제안 로드맵)

| 단계 | 범위 | 목표 |
|---|---|---|
| Phase 1 (MVP) | 서버 등록/관리(테이블 뷰 포함) + SSH 클라이언트(터미널, 동시 명령 실행 포함) + 보안 기반(수동 인증·로컬 데이터 암호화·접속 로그·세션 강제종료) | 매일 쓰는 SSH부터 대체하면서 ISMS 심사 가능한 보안 기반을 처음부터 구축 |
| Phase 2 | SFTP/FTP 통합 | 파일 전송까지 커버 |
| Phase 3 | tmux 세션 유지 기능 고도화(분할/멀티플렉싱) | Termius 유료 기능 대체 |
| Phase 4 | RDP 클라이언트 | Windows 서버 커버 |
| Phase 5 | VNC 클라이언트 + Web 콘솔 등록 | 전체 프로토콜 커버 완성 |

## 8. 리스크 및 고려사항

- **RDP/VNC 프로토콜 자체 구현 난이도**: 오픈소스 라이브러리(FreeRDP 등) 연동 검토 필요, 라이선스 확인 필수
- **자동로그인 폐기에 따른 UX 저하**: 매 접속마다 비밀번호를 직접 입력해야 하므로 타이핑 빈도가 높아짐 → SSH Key(패스프레이즈 없는 키 포함) 인증을 기본 권장 방식으로 안내해 마찰 최소화 (Key 인증은 심사 요구사항의 대상이 아님)
- **크로스플랫폼 이슈**: Windows/Mac 각각 네이티브 API 차이(클립보드 공유, 드라이브 마운트 등)
- **범위 확장 리스크**: 5개 프로토콜을 동시에 다 만들려 하면 일정 지연 → MVP는 SSH부터 좁게 시작 권장
- **ISMS 심사 대응 리스크**: 실제 심사 시 조직마다 요구 수준이 다를 수 있음(국정원 검증필 암호모듈(KCMVP) 요구 여부 등) → 초기엔 AES-256 등 업계 표준으로 설계하고, 심사 범위 확정 시 재점검 필요
